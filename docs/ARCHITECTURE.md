# نظرة معمارية عامة

## المشاريع الثلاثة

| المشروع | النوع | الدور |
|---|---|---|
| `Aman.Shared` | مكتبة (.NET class library, `net8.0-windows`) | التشفير (AES-256-GCM)، اشتقاق المفاتيح (PBKDF2+HKDF)، معرّف الجهاز (WMI)، صيغة الحاوية (قراءة/كتابة)، نظام التوقيع/الأكواد (ECDSA)، الترجمة (ar/en)، تبديل السمة (Dark/Light) |
| `Aman.Encoder` | تطبيق WPF (`WinExe`) | واجهة البائع: إضافة/ترتيب الفيديوهات، إعدادات الحماية والعلامة التجارية، بناء الحزمة، توليد أكواد التفعيل |
| `Aman.Player` | تطبيق WPF (`WinExe`, يُنشر باسم `Player.exe`) | الملف الموزَّع للمستخدم النهائي: يقرأ الحاوية المُلحقة بنفسه، يتحقق من كلمة السر/كود التفعيل، يشغّل قائمة التشغيل |

## تدفق البناء (Encoder → EXE موزَّع)

```
مستخدم Encoder يضيف فيديوهات + كلمة سر + إعدادات
        │
        ▼
ContainerBuildRequest (Aman.Shared)
        │
        ▼
ContainerWriter.BuildAsync:
  1. يشتق KEK من كلمة السر (PBKDF2 + HKDF)
  2. لكل فيديو: يولّد مفتاح AES-256 عشوائي، يغلّفه بـ KEK
  3. يشفّر الفيديو على شكل قطع AES-256-GCM (streaming من القرص، بلا تحميل كامل بالذاكرة)
  4. يبني رأس الحاوية (ويوقّعه إن وُجدت هوية بائع)
        │
        ▼
PackageBuilderService:
  ينسخ بايتات Player.exe (المبني مسبقًا) → يُلحق الحاوية → يُلحق trailer
        │
        ▼
   ملف EXE واحد جاهز للتوزيع
```

## تدفق التشغيل (Player.exe عند المستخدم النهائي)

```
تشغيل Player.exe
        │
        ▼
SelfExeLocator: يجد بداية الحاوية داخل نفسه (عبر الـ trailer في النهاية)
        │
        ▼
ContainerReader: يقرأ الرأس، يتحقق من التوقيع إن وُجد
        │
        ▼
شاشة فتح القفل: كلمة سر [+ كود تفعيل إن كانت الحزمة تتطلبه]
        │  (تحقق: verifier PBKDF2/HKDF، توقيع ECDSA، الجهاز، الانتهاء، عدد المرات)
        ▼
فك تغليف مفاتيح كل فيديو في الذاكرة (KEK مشتق من كلمة السر)
        │
        ▼
SecurePlaybackServer: خادم HTTP محلي (127.0.0.1) يفك القطع المطلوبة عند الطلب فقط
        │
        ▼
MediaElement (محرك ويندوز المدمج) يشغّل من رابط http://127.0.0.1:PORT/...
        │
        ▼
AntiCaptureService: يستثني النافذة من واجهات التقاط الشاشة القياسية + يمنع مفتاح PrintScreen
```

## قرارات تصميم رئيسية ولماذا

- **محرك تشغيل الفيديو**: `MediaElement` (Media Foundation المدمج في ويندوز) بدل مكتبة خارجية
  (مثل LibVLC) — يبقي التوزيع **ملفًا تنفيذيًا واحدًا فعليًا** بدون DLLs إضافية، وهذا كان
  شرطًا صريحًا في المتطلبات. الثمن: `MediaElement` لا يقبل مصدر بيانات في الذاكرة مباشرة، لذا
  استُخدم خادم HTTP محلي (loopback) كوسيط — انظر `docs/CONTAINER_FORMAT.md`.
- **AES-256-GCM على شكل قطع (chunked)** بدل تشفير الملف كوحدة واحدة — يتيح البحث (seek) في
  الفيديو دون فك كل شيء من البداية.
- **ECDSA (مفتاحان) بدل سر مشترك** لنظام الأكواد — يمنع استخراج سر التوقيع من نسخة موزَّعة.
  راجع `docs/LICENSING_SYSTEM.md`.
- **بلا خادم مركزي (fully offline)** — بالتصميم، بناءً على طبيعة الطلب (أداة تُوزَّع كملف
  EXE مستقل يعمل "على أي جهاز ويندوز بدون تثبيت"). هذا يعني أن حدود الاستخدام (تاريخ الانتهاء،
  عدد المرات) قابلة للتصفير محليًا من مستخدم لديه صلاحيات كافية على جهازه؛ موثَّق بوضوح في كل
  مكان ذي صلة بدلًا من الادّعاء بحماية مطلقة.

## ماذا لو أردت لاحقًا إضافة تحقق عبر خادم (اختياري مستقبلي)؟

التصميم الحالي لا يتضمن أي اتصال شبكي في `Player.exe` (باستثناء الخادم المحلي loopback). لو
احتجت لاحقًا تحققًا مركزيًا (مثال: تعطيل حزمة معيّنة عن بُعد، أو منع تجاوز عدد الأجهزة الفعلي
لا المحلي فقط)، أضِف نداء HTTPS اختياريًا بعد التحقق المحلي الناجح، مع الإبقاء على المسار
الحالي كخيار احتياطي (fallback) عند غياب الإنترنت — هذا خارج نطاق هذا التسليم الحالي عمدًا حفاظًا
على مطلب "يعمل بدون تثبيت أي شيء" و"مستقل".
